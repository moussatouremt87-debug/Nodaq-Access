## 0. Ce qu'on construit, en une phrase

Un agent vocal qui **appelle les débiteurs d'un tenant pour relancer une facture
impayée**, de façon autonome pendant l'appel — mais jamais autonome dans la décision
d'appeler : chaque appel est une `pending_action` validée par le dirigeant (règle 4 de
CLAUDE.md, non négociable).

Premier cas d'usage : la relance d'impayés. L'architecture doit rester généralisable
(confirmation de rendez-vous, rappel d'échéance) mais **n'implémente que la relance**
dans ce ticket.

## 1. Stack imposée — et pourquoi

| Couche | Choix | Justification |
|---|---|---|
| Orchestration temps réel | **LiveKit Agents**, auto-hébergé (infra Scaleway) | Open-source, SIP sortant natif, souveraineté possible. Pas de Vapi/Retell/Bland : SaaS US, les conversations (données `confidentiel`) sortiraient du tier souverain — contraire à la règle 1. |
| STT | **Gladia** (temps réel) ou **Voxtral** (Mistral) — abstraire derrière une interface, trancher en phase 1 sur un benchmark latence/qualité FR | Les deux restent dans le cadre souverain. |
| LLM | **Chaîne existante : `packages/classifier` → LiteLLM → Mistral EU / Scaleway** | Aucune exception : l'agent vocal est un consommateur de la chaîne existante, jamais un SDK fournisseur en direct. |
| TTS | **Voxtral TTS** (open-weight, auto-hébergé) | Ferme la boucle 100 % souveraine. Pas d'ElevenLabs (US). |
| Téléphonie | **Telnyx** (décision fondateur), trunk SIP branché sur LiveKit SIP — toujours derrière une interface `TelephonyProvider` | Intégration LiveKit documentée, numéros FR disponibles. L'interface reste obligatoire : Telnyx est un choix de départ, pas un couplage — une migration vers un opérateur FR (OVHcloud) doit rester un changement d'implémentation, pas une refonte. |
| VAD / tour de parole | Silero VAD (intégré LiveKit) | L'agent se tait quand on l'interrompt — non négociable pour l'acceptabilité. |
| Observabilité | Langfuse + OpenTelemetry, comme le reste | Chaque appel = une trace ; jamais l'audio brut dans les logs (règle 5). |

Emplacement : nouveau service **`services/voice`** (Python, FastAPI + worker LiveKit
Agents), piloté par `apps/agent-runtime` via BullMQ. Ne pas mettre la logique d'appel
dans l'API TypeScript.

## 2. User stories — le périmètre EXACT du ticket

### US-1 — Valider une campagne de relance, mandat de négociation inclus
**En tant que** dirigeant, **je veux** valider en un clic la liste des appels de
relance proposés par nodaq (qui, quelle facture, quel montant, quand) **et voir/
ajuster le mandat de négociation au même endroit**, **afin que** rien ne parte sans
mon accord — ni la liste des appels, ni ce que l'agent a le droit d'accorder.
- Critères : la proposition arrive dans la file `pending_action` existante (pas un
  nouveau mécanisme) ; je peux exclure un débiteur de la liste avant validation ;
  aucun appel n'est composé sans `pending_action` approuvée ; la validation d'une
  campagne vaut pour ses appels listés, pas pour les suivants.
- **Le mandat est visible et ajustable dans l'écran de validation du cockpit** :
  la carte de validation affiche, sous la liste des appels, un panneau « Ce que
  l'agent peut accorder » pré-rempli depuis la règle du tenant (US-9) — échelonnement
  oui/non et nombre max, date limite de règlement, lien de paiement, remise. Le
  dirigeant peut **restreindre** le mandat pour cette campagne (ex. désactiver
  l'échelonnement pour un débiteur récidiviste), jamais l'élargir au-delà de la
  règle du tenant. Le mandat effectif est figé dans la `pending_action` au moment de
  l'approbation — le modifier ensuite exige une nouvelle validation.

### US-2 — L'agent s'annonce et propose une sortie
**En tant que** débiteur appelé, **je veux** savoir immédiatement que je parle à un
assistant automatique et pouvoir demander un humain ou un rappel, **afin de** ne
jamais me sentir piégé.
- Critères : annonce en début d'appel (« assistant automatique de [nom de
  l'entreprise] ») — transparence AI Act, non désactivable ; à tout moment, « je veux
  parler à quelqu'un » → l'agent prend note, clôt poliment, crée une tâche de rappel
  humain dans le cockpit ; l'agent ne rappelle jamais plus de `maxAttempts` fois
  (défaut 3) ni en dehors de la fenêtre d'appel configurée (défaut 9h-18h, jours
  ouvrés, fuseau du tenant).

### US-3 — Obtenir une promesse de paiement ferme (autonomie encadrée par mandat)
**En tant que** dirigeant, **je veux** que l'agent ait une vraie marge de manœuvre
pendant l'appel pour repartir avec une promesse ferme — pas un vague « je verrai » —
**afin que** l'appel produise un engagement exploitable, pas juste un compte-rendu.

L'autonomie de l'agent est définie par un **mandat de négociation** à deux étages :
la **règle du tenant** (US-9, configurée une fois dans les paramètres) fixe le
plafond de ce qui est négociable dans l'entreprise, et le **mandat de campagne**
(US-1, ajusté à la validation) peut restreindre ce plafond pour une campagne donnée —
jamais le dépasser. C'est le mécanisme clé : l'agent est autonome *à l'intérieur* du
mandat effectif, jamais au-delà. Structure indicative :

```ts
negotiationMandate: {
  canOfferInstallments: boolean;   // proposer un échelonnement
  maxInstallments: number;         // ex. 3
  minFirstPaymentDays: number;     // 1er versement sous X jours max
  latestAcceptableDate: Date;      // date de règlement la plus tardive acceptable
  canSendPaymentLink: boolean;     // proposer un lien de paiement par SMS pendant l'appel
  canOfferDiscount: false;         // remise : désactivé par défaut, activable explicitement
}
```

- Critères d'acceptation :
  - Réponse vague (« bientôt », « dès que possible ») → l'agent **insiste poliment,
    au plus deux fois**, pour obtenir une date et un montant précis (« quel jour
    exactement puis-je noter ? »).
  - Dans les limites du mandat, l'agent peut proposer de lui-même un échelonnement
    ou un lien de paiement immédiat par SMS si ça débloque la conversation.
  - **Cas explicite — le débiteur demande à payer en plusieurs fois.** Trois issues
    selon la configuration, dans cet ordre de vérification :
    1. Échelonnement autorisé par la règle du tenant **et** actif dans le mandat de
       cette campagne → l'agent négocie l'échéancier dans les limites
       (`maxInstallments`, `minFirstPaymentDays`, `latestAcceptableDate`), le
       verrouille par reformulation, et chaque versement devient une échéance
       suivie au cockpit.
    2. Autorisé par la règle du tenant **mais** désactivé dans le mandat de cette
       campagne → l'agent n'accorde pas : « je note votre demande, [le dirigeant]
       revient vers vous » ; la demande remonte comme tâche à décider, avec
       l'échéancier demandé pré-rempli pour validation en un clic.
    3. Non autorisé par la règle du tenant → même comportement que 2, mais la tâche
       remontée signale aussi au dirigeant que sa règle actuelle interdit
       l'échelonnement, avec un lien vers le paramètre (US-9) s'il veut la changer —
       la règle ne se modifie jamais depuis l'appel lui-même.
  - Toute promesse est **verrouillée par une reformulation explicite** avant de
    clore (« je récapitule : vous réglez X € le [date], c'est bien ça ? ») — pas de
    promesse enregistrée sans confirmation verbale du débiteur.
  - Une demande hors mandat (délai au-delà de `latestAcceptableDate`, plus
    d'échéances que `maxInstallments`, remise non autorisée) → l'agent ne l'accorde
    jamais : il prend note, clôt, et remonte la demande au dirigeant comme tâche à
    décider.
  - L'échéance (ou l'échéancier) créé est visible dans le cockpit, rafraîchi via le
    bus d'événements (#86) ; promesse non tenue à J+1 → nouvelle `pending_action`
    proposée (jamais déclenchée seule).

### US-4 — Négocier dans le mandat, jamais s'acharner
**En tant que** dirigeant, **je veux** que l'agent négocie fermement mais reste dans
des limites strictes, **afin de** ne jamais dégrader ma relation client ni franchir
la ligne du harcèlement.
- Critères : la persuasion autorisée est **positive uniquement** (faciliter le
  paiement : date précise, échelonnement, lien immédiat — voir mandat US-3) ; jamais
  de pression négative : pas de menace, pas de « mise en demeure », pas d'allusion au
  contentieux, pas de culpabilisation, pas plus de deux insistances sur la date dans
  un même appel ; si le débiteur conteste la facture → l'agent ne débat pas, consigne
  la contestation, clôt, crée une tâche humaine ; si le débiteur s'énerve ou demande
  d'arrêter → l'agent clôt immédiatement et poliment (le cadre légal du recouvrement
  amiable sanctionne l'appel répété ou oppressant — l'insistance vit *dans* l'appel,
  jamais par multiplication des appels) ; ton calme et factuel — les garde-fous sont
  dans le prompt système ET vérifiés par des évals (voir §5).

### US-5 — Répondeur et non-réponse
**En tant que** dirigeant, **je veux** un comportement propre en cas d'absence,
**afin que** la relance reste professionnelle.
- Critères : répondeur détecté → message sobre de 15 s max (qui appelle, de la part
  de qui, rappeler à quel numéro), sans montant   ni mention de dette (un répondeur
  peut être écouté par des tiers — confidentialité) ; nouvel essai selon la politique
  `maxAttempts`/fenêtre horaire ; après épuisement, l'issue « injoignable » est
  remontée au cockpit avec suggestion de passage à la relance écrite.

### US-6 — Compte-rendu dans le cockpit
**En tant que** dirigeant, **je veux** voir pour chaque appel l'issue, le résumé et la
transcription, **afin de** garder la main sans réécouter les appels.
- Critères : issue typée (`promise | dispute | callback_requested | unreachable |
  refused | paid_claimed`), résumé 3 lignes généré via la chaîne LLM habituelle,
  transcription complète consultable ; tuile cockpit mise à jour en temps réel (bus
  d'événements) ; coût de l'appel (minutes STT/TTS/téléphonie) tracé par appel pour
  la facturation à l'usage prévue au pricing v2.

### US-7 — Opt-out définitif
**En tant que** débiteur, **je veux** pouvoir dire « ne me rappelez plus », **afin
que** ce choix soit respecté.
- Critères : détection de la demande en appel → flag `doNotCall` sur le contact du
  tenant, effectif immédiatement, visible dans le cockpit ; aucun appel ultérieur
  vers ce contact tant que le dirigeant n'a pas explicitement levé le flag (avec
  avertissement).

### US-8 — RGPD de bout en bout
**En tant que** responsable de traitement, **je veux** que l'appel respecte le cadre
déjà construit, **afin de** ne pas créer une zone grise dans un produit qui vend la
conformité.
- Critères : annonce d'enregistrement en début d'appel si enregistrement activé ;
  l'audio brut n'est **pas conservé** par défaut (transcription seule, cohérent avec
  « audio souverain, jamais conservé » du devis dicté #77) ; transcriptions et
  résumés entrent dans la cascade d'effacement art. 17 (#84/#85) — effacer le contact
  efface ses appels, transcriptions, promesses dérivées ; le test d'effacement le
  prouve.

### US-9 — La règle de négociation du tenant, configurée en amont
**En tant que** dirigeant (rôle OWNER), **je veux** définir une fois pour toutes,
dans les paramètres du cockpit, ce que l'agent a le droit de négocier dans mon
entreprise, **afin que** chaque validation de campagne parte d'une politique réfléchie
à froid — pas d'un choix fait dans l'urgence à chaque relance.
- Critères :
  - Écran « Règles de relance » dans les paramètres : échelonnement autorisé oui/non,
    nombre max de versements, délai max du premier versement, retard max acceptable
    sur la date de règlement, lien de paiement oui/non, remise oui/non (défaut : non).
  - Réservé au rôle `OWNER` (`requireRole`) — un `MEMBER` valide des campagnes dans
    le cadre de la règle, il ne modifie pas la règle.
  - La règle est versionnée : chaque mandat de campagne référence la version de la
    règle en vigueur au moment de la validation — un changement de règle ne modifie
    jamais rétroactivement une campagne déjà validée.
  - Valeurs par défaut prudentes à la création du tenant : échelonnement désactivé,
    remise désactivée — l'autonomie de négociation est un choix explicite, jamais un
    défaut silencieux.
  - Le panneau de mandat de l'écran de validation (US-1) se pré-remplit depuis cette
    règle et affiche clairement quand la campagne restreint la règle.

## 3. Modèle de données (indicatif — à confirmer sur le schéma réel en plan mode)

- `TenantNegotiationPolicy` : `tenantId`, champs de la règle (US-9), `version`,
  `updatedBy`, `updatedAt` — versionnée, jamais écrasée en place.
- `CallCampaign` : `tenantId`, `status`, `pendingActionId`, fenêtre d'appel, liste
  d'appels, `mandate` (mandat effectif figé à la validation) +
  `policyVersionRef` (version de la règle tenant appliquée).
- `OutboundCall` : `tenantId`, `campaignId`, `contactId`, `invoiceId`, `attempt`,
  `status`, `outcome`, `promisedAmount`, `promisedDate`, `transcript`, `summary`,
  `costBreakdown`, `startedAt/endedAt`.
- Flag `doNotCall` sur le contact (ou table dédiée si le contact est partagé).
- **Chaque nouvelle table : `tenantId` + policy RLS + test d'isolation qui échoue si
  on retire la policy (règle 6). Aucune exception.**
- Secrets (SIP, Gladia/Mistral) : `.env` dev / Secret Manager prod, jamais loggés.

## 4. Phases d'implémentation

1. **Plan mode** : lire l'existant (`pending_action`, bus d'événements, effacement,
   BullMQ, `services/*` Python), produire le plan — y compris le benchmark
   STT (Gladia vs Voxtral, latence + qualité FR au téléphone) et le choix
   d'intégration LiveKit (self-host sur l'infra `ops/` en dev). Ne rien coder avant
   validation.
2. **Modèle de données en TDD** (tables + RLS + tests d'isolation + cascade
   d'effacement).
3. **Service `services/voice`** : worker LiveKit Agents, interfaces
   `SpeechToText` / `TextToSpeech` / `TelephonyProvider` (implémentations
   interchangeables), pipeline complet testable en local **sans vraie ligne SIP**
   (mode simulation : audio in/out par fichiers ou WebRTC local).
4. **Intégration** : `pending_action` → job BullMQ → appel → issues → bus
   d'événements → cockpit. Réutiliser, ne pas dupliquer.
5. **Garde-fous + évals** : suite d'évals conversationnelles (scénarios : promesse
   directe, réponse vague → insistance pour une date précise, demande d'échelonnement
   dans le mandat → accordée, demande hors mandat → refusée et remontée, contestation,
   demande d'humain, agressivité → clôture immédiate, opt-out, répondeur, **et les
   trois variantes de la demande d'échelonnement de l'US-3 — accordée dans le mandat,
   remontée si désactivée en campagne, remontée avec signalement si interdite par la
   règle tenant**) rejouées sur le pipeline complet en simulation — l'éval échoue si
   l'agent dépasse le mandat,
   menace ou culpabilise, insiste plus de deux fois, clôt sans reformulation de la
   promesse, oublie de s'annoncer, ou rappelle un `doNotCall`.
6. **Vérification** : `pnpm lint && pnpm typecheck && pnpm test` + `uv run ruff
   check && uv run mypy && uv run pytest` verts, évals du workflow passées, puis
   sous-agent `rgpd-security-reviewer` sur le diff complet.

## 5. Ce que tu ne dois PAS faire

- Composer un appel sans `pending_action` approuvée — y compris « juste pour tester »
  en staging : le mode simulation existe pour ça.
- Brancher Vapi, Retell, Bland, ElevenLabs ou tout SaaS vocal hors UE.
- Appeler un LLM sans passer par `classifier` → LiteLLM.
- Conserver l'audio brut par défaut, ou logger un extrait de conversation.
- Laisser l'agent sortir de son mandat de négociation (remise non autorisée, délai
  au-delà de la limite), parler de contentieux, ou rappeler hors fenêtre horaire.
- Coupler le code métier au fournisseur SIP ou au fournisseur STT (interfaces
  obligatoires).
- Exposer une UI « relance vocale » aux tenants avant que la suite d'évals passe et
  qu'un test réel supervisé ait été fait sur les numéros de l'équipe.

## 6. À trancher avec le fondateur avant la phase 3

- ~~Fournisseur SIP~~ → **tranché : Telnyx** (voir §1). Point d'attention à
  documenter dans le plan : Telnyx est un fournisseur américain — le média voix
  transite par son infrastructure. Les conversations restant classées
  `confidentiel`, vérifier en phase 1 la configuration de résidence des données
  EU de Telnyx et consigner la décision dans un court ADR ; la migration
  ultérieure vers un opérateur FR reste couverte par l'interface
  `TelephonyProvider`.
- ~~Enregistrement audio~~ → **tranché : transcription seule, pas de conservation
  d'audio** (cohérent avec « audio souverain, jamais conservé », #77). L'annonce
  d'enregistrement en début d'appel devient donc une annonce de transcription.
- Tarification à l'usage de la relance vocale (pricing v2) : prix par appel abouti ou
  par minute — hors périmètre du code de ce ticket, mais `costBreakdown` doit fournir
  la donnée pour les deux options.
