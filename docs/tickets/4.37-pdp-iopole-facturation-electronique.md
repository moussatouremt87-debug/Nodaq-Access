## 0. Contexte réglementaire (état au 22/08/2026)

- **1er septembre 2026** : TOUTE entreprise assujettie à la TVA doit pouvoir
  RECEVOIR des factures électroniques. Grandes entreprises et ETI doivent émettre.
- **1er septembre 2027** : PME, TPE et micro doivent ÉMETTRE + e-reporting.
- Le flux passe par des Plateformes Agréées (PA/PDP) immatriculées par la DGFiP,
  interconnectées via l'annuaire et le PPF.

Conséquence produit : dans 10 jours, chacun de nos tenants doit avoir une adresse
de réception. C'est aussi notre meilleur argument commercial 2026-2027 : le marché
entier change d'outil pour ça.

## 1. Pourquoi IOPOLE comme candidat n°1

- **PA immatriculée DGFiP n° 0018** — agrément réel, pas une promesse.
- **API-first, pensée marque blanche pour les éditeurs** : API REST + webhooks,
  l'expérience reste dans nodaq (exactement notre doctrine ; c'est le modèle
  qu'Obat a retenu).
- Formats **Factur-X, UBL, CII**, cycle de vie complet des statuts (déposée,
  reçue, acceptée, refusée…), **Peppol** pour l'international.
- **ISO 27001 + SecNumCloud**, archivage à valeur probante — compatible avec
  notre registre de souveraineté (sous-traitant français, à documenter).
- Tarification non publique : setup + coût au volume → à négocier (phase 1).

## 2. Phase 1 — Étude et contact (livrable : note de décision, PAS de code)

1. Contacter IOPOLE (offre partenaires/éditeurs) : conditions d'accès API,
   sandbox, tarifs setup + volume pour un éditeur early-stage, délais
   d'onboarding d'un tenant, gestion de l'annuaire, e-reporting inclus ?
2. Comparer avec 1 ou 2 alternatives PDP orientées API (pour le levier de
   négociation et la clause de sortie) : mêmes questions.
3. Vérifier les points de souveraineté : localisation des données, sous-traitants
   d'IOPOLE, DPA — entrée registre + ADR à préparer.
4. Me livrer une note : coût par tenant/mois estimé, effort d'intégration,
   risques, recommandation. **STOP : validation fondateur avant la phase 2.**

## 3. Phase 2 — Intégration (après validation)

**Interface `EInvoiceProvider`** (`packages/einvoice`) — réversibilité comme
toujours : `registerTenant` (rattachement à l'annuaire), `sendInvoice`,
`receiveWebhook` (factures entrantes + changements de statut), `getStatus`,
`downloadDocument`.

- **Réception d'abord** (échéance 09/2026) : chaque tenant activé reçoit ses
  factures fournisseurs dans nodaq → elles alimentent le module Achats et la
  lecture automatique existante (une facture reçue par la PDP arrive DÉJÀ
  structurée : plus besoin d'OCR pour celles-là).
- **Émission ensuite** (échéance 09/2027) : le PDF Factur-X du 4.24 part par la
  PDP ; statuts (déposée/reçue/refusée) remontés dans la fiche facture et le
  bus (#86) ; un REFUS déclenche une notification et une proposition de
  correction par l'agent (via pending_action).
- **E-reporting** : transmis via la PDP pour les transactions hors périmètre
  (B2C, international) — cadré en phase 1.
- **Onboarding tenant** : le parcours guidé de la bannière (4.36 Lot B) —
  vérification d'identité selon les exigences IOPOLE, rattachement annuaire,
  écran « ✓ Vous êtes prêt ». Objectif : le « en 2 minutes, c'est réglé » d'Obat,
  en mieux expliqué.
- Webhooks : signature vérifiée, idempotence, tenant résolu depuis identifiant
  signé — mêmes règles que 4.18-bis et 4.21.
- Registre des sous-traitants + ADR mis à jour AVANT la mise en production ;
  l'attestation de souveraineté doit refléter le nouveau périmètre.

## 4. Ce que tu ne dois PAS faire

- Lancer la moindre intégration avant la note de décision validée (des frais de
  setup se négocient, pas s'improvisent).
- Construire quoi que ce soit qui nous rapproche d'un statut de PA en propre :
  c'est un chantier réglementaire à capital que nous refusons explicitement.
- Coupler le code métier à l'API IOPOLE hors de l'adaptateur.
- Afficher « conforme » à un tenant dont le rattachement annuaire n'est pas
  confirmé par la PDP.

## 5. Vérification

Phase 1 : note de décision livrée, chiffrée, avec recommandation et clause de
sortie. Phase 2 : e2e sandbox — réception d'une facture test → module Achats ;
émission Factur-X → statuts remontés ; webhook rejoué → idempotent. Registre,
ADR, attestation cohérents. `rgpd-security-reviewer` sur le diff complet
(nouveau sous-traitant + webhooks entrants : périmètre maximal).
